# GoalJourney — project memory for Claude Code

GoalJourney helps one user reach one personal goal. This repository holds the **dataset,
validation and evaluation pipeline** for *GoalJourney Navigator*: a specialised ~4B open-weight
model that clarifies a goal, builds a living route (the Journey), verifies progress from evidence,
and adapts the route. It is not the mobile app, and the navigator is not a general assistant.

## Start of every large task

1. Run `/start-session`, or read `docs/PROJECT_STATE.md`, `docs/ACTIVE_MILESTONE.md`,
   `docs/DECISIONS.md` and `docs/ROADMAP.md`, then `git status` and `git log --oneline -10`.
2. Work within the active milestone. If a request falls outside it, confirm scope first.
3. The repository is the source of truth, not chat history (`docs/CONTEXT_MANAGEMENT.md`).
   Never ask the user to paste an earlier conversation.

## Product principles (full list: `docs/DECISIONS.md`)

- The user controls the Journey. The navigator proposes; major route changes and goal changes need
  confirmation; verified progress is never silently discarded.
- Deadline autonomy:
  - task dates may adapt automatically;
  - milestone dates may adapt with a stated summary;
  - goal dates are only proposed until the user confirms.
- A photo alone never verifies a task. Self-report is valid but capped at *limited* confidence.
  Insufficient evidence leads to `needs_more_evidence`, not rejection.
- Use and promise only capabilities the product has (`configs/product_capabilities.yaml`): no video
  analysis, reminders, calendar access, API calls or account access.
- Levels and achievements follow verified progress, never app activity.
- Safety: no medical, legal or financial prescriptions; referrals where needed; restricted goals
  are declined with a legitimate alternative.

## Non-negotiable data and privacy rules

- Never commit secrets. Credentials come only from the environment or the git-ignored `.env`.
- The dataset contains no real user data, and user data never enters training automatically.
- Automation never approves. Never record, invent or imply a human review decision.
  `review/reviewers.yaml` lists humans only, and validation passing is not a review.
- Releases are immutable. Every content change needs a new `dataset_version` and a revision-ledger
  entry (`data/revisions/`); no silent edits. v0.1.0 artefacts are frozen.
- Never loosen release gates, tests or validators to make something pass.
- Never infer a user's gender or pronouns. Russian output is gender-neutral.
- No model training unless the active milestone calls for it **and** `gj gates` passes.

## AI behaviour the dataset teaches

- Ask only questions whose answers change the plan; never re-ask what is known.
- Dates, weekdays and hour arithmetic must follow from the calendar and the plan.
- Facts keep their provenance: user_provided, model_inferred, externally_verified or unknown.
  Current external facts come only from provided research.
- Answer in the user's language, and state limits honestly rather than pretend a capability.
- Train the future-correct behaviour, but only with capabilities the product can represent
  (`docs/POLICY_DECISIONS_v0.1.1.md`).

## Repository conventions

- Python ≥ 3.10. CLI: `python3 scripts/gj.py <command>` (called `gj` below). Full gate: `make check`.
- Versions live only in `configs/versions.yaml`. Schemas are in `schemas/`, older versions in
  `schemas/archive/`, and records are validated against their own `schema_version`.
- Training examples: `data/raw/examples/*.yaml`. Evaluation cases are **generated** from
  `evaluation/builders/`; never hand-edit `evaluation/cases/v0.2.0/*.yaml`.
- Derived files are regenerated by their command, never edited by hand:

  | File | Regenerate with |
  |---|---|
  | releases | `gj split` |
  | `review/audit_findings_v*.json` | `gj audit --write` |
  | `review/review_sample_status_v*.json` | `gj review sample-status --write` |
  | ledger hashes | `gj revisions sync` |
  | eval YAML | `gj eval build-cases` |

- Spec: `DATASET_SPEC.md` (read the section you need). Policies:
  `docs/POLICY_DECISIONS_v0.1.1.md`.
- New behaviour gets a test in `tests/`. Subsystem details are in the path-scoped rules
  (`.claude/rules/`).

## Critical commands

| Command | Purpose |
|---|---|
| `gj validate` | ~4 s; must end with `RESULT: PASS` |
| `python3 -m pytest -q` | full test suite |
| `make check` | validate, tests, drift checks (eval builder, ledger, review sample), eval self-check, leakage, review log (~2 min) |
| `gj revisions check` | the ledger accounts for every change since the base release |
| `gj eval build-cases --check` | the eval YAML matches its builders |
| `gj gates` | release gates; expected to fail until human review is done |

## Milestone workflow

- One major milestone per primary session. Start a fresh session after completing it.
- At checkpoints, commit and update the Progress and Next action sections of
  `docs/ACTIVE_MILESTONE.md`, so a new session can resume.
- Before declaring a milestone complete, run `/milestone-complete`:
  1. tests and validation;
  2. diff review;
  3. update the `PROJECT_STATE`, `ACTIVE_MILESTONE`, `DECISIONS`, `ROADMAP` and `CHANGELOG` files;
  4. report unresolved issues;
  5. commit.

  Never claim completion from tests alone.

## Skills, subagents and context

- Skills, loaded on demand:

  | Skill | Use |
  |---|---|
  | `/start-session` | recover state at the start of a session |
  | `/milestone-complete` | completion protocol |
  | `/dataset-review` | human-review round |
  | `/dataset-generation` | synthetic generation |
  | `/evaluation` | eval cases and runs |
  | `/release-check` | releases, gates, pre-training checks |

- Subagents (`.claude/agents/`): `dataset-auditor`, `evaluation-engineer`,
  `verification-reviewer`, `safety-reviewer`, `architecture-reviewer`, `code-reviewer`.
  - **Use one** when many files must be read but only findings are needed, when independent analyses
    can run in parallel, or when a specialist review helps.
  - **Don't** for simple sequential edits, one- or two-file tasks, or work that needs detailed
    step-to-step context.
- Keep this file under 200 lines. Datasets, eval cases, transcripts, reports, schemas and subsystem
  notes belong elsewhere (`docs/CONTEXT_MANAGEMENT.md` §9).
- Don't read large files whole: release JSONL, revision snapshots, audit JSON, generated eval YAML.
  Use `grep` or `head`, the matching `gj` command, or a subagent.
- Check `/context` after big exploratory steps and use `/compact <focus>` at natural breakpoints.
  Auto-compaction stays on, at a 75% threshold (`.claude/settings.json`).

## Git

- Work on the branch the session designates, and push only there. Never rewrite pushed history,
  force-push, or amend milestone commits.
- Keep `.env`, model checkpoints, exports and caches out of git (`.gitignore`). Do not commit
  generated reports under `evaluation/reports/`.
